# 安全

Sync Engine 处理你的仓库文件、远端存储凭据和可执行模块。本页说明它信任什么、不能保护什么，以及你能做什么来降低风险。

## 信任边界

Sync Engine 信任本地操作系统、Obsidian 和运行它的设备。任何能控制你的设备或 Obsidian 会话的人或软件，也可能访问你的仓库和配置的凭据。Sync Engine 无法防护已被攻破的设备。

Sync Engine 也假定用户对自己的安全是理性的：只要用户明确批准，它允许一切。

模块是可执行代码。启用的模块可以获得广泛的 Obsidian 和 Sync Engine 权限，包括仓库文件和网络请求。这是可扩展设计的必然结果，但这也意味着你应该像对待插件一样对待模块，只启用你信任的模块。

没有客户端加密时，你同步的文件会到达配置的后端。因此，后端和网络都应被视为你的数据可能被读取或修改的地方。[加密模块](../deep-dive/modules/encryption)让客户端在上传前加密文件内容和文件名。它不能隐藏所有细节：后端仍然可以得知文件大小、修改时间、文件数量等信息，也仍然可以删除或回滚远端数据。

## Sync Engine 做了什么

- 只有配置的后端和模块源会收到请求。Sync Engine 没有遥测。请求的时机和范围见[权限](./permissions)。
- 新模块默认禁用。Sync Engine 把你的批准记录与模块文件分开保存，并在加载前检查模块完整性，除非你显式关闭该检查。确切的边界见[扩展性契约](../deep-dive/extensibility)。
- 自动更新只作用于来自同一来源的已安装模块。一个从未有过下载记录的新模块会触发明确的潜在恶意警告。
- 官方模块只读取其文档所述功能需要的密钥。密钥通过 Obsidian 的密钥存储保存，而不是普通设置。
- 每个官方模块在获得"官方"称号之前，都经过负责任的真实人类维护者审查。

这些防护减少了意外或未经授权的模块执行。在你批准并启用之后，它们不能让一个不可信的模块变得安全。源码链接和完整性检查是有用的证据，不能替代你的判断。

## 提升你的安全性

- 从你认识的来源安装模块。启用前审查模块的源码和它请求的功能，移除不再信任的模块源。
- 保持完整性验证开启。除非你明白为什么必须这样做，不要批准不可信的模块或关闭验证。
- 避免 HTTP 源，尤其是在你无法控制的网络上。后端和模块源 URL 使用 HTTPS
- 对敏感仓库启用加密模块。使用强而唯一的密码，保存在 Obsidian 的密钥存储中，并在同步加密文件之前在每台设备上配置好。依赖它之前请阅读[加密规范](../deep-dive/modules/encryption)。
- 用操作系统的更新、账户保护和磁盘加密（如果可用）保护你的设备和 Obsidian 仓库。
- 只给你的后端账户授予 Sync Engine 所用目录的访问权限，并保留独立的备份。加密无法找回被恶意后端删除的数据。
