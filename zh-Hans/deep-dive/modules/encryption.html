客户端加密 v2.1 ​

插件把加密后的文件上传到远端，下载后解密回本地。本文规定 Encryption 模块中加密算法的实现。

本模块的加密实现欢迎自愿审计。

术语 ​

记号 ​

  • IV = 初始化向量 = Nonce
  • B = 字节（Byte）
  • b = 比特（bit）
  • 1KiB = 1024B
  • || = 拼接

威胁模型与约束 ​

实现信任：

  • 客户端在模块之外共享密码。共享渠道不在范围之内，模块不需要实现自己的密钥交换。
  • 操作系统或 Obsidian 运行时未被攻破。

实现不信任：

  • 后端服务器
  • 传输层

实现防护：

  • 未授权访问
  • 未授权修改或文件截断
  • 加密与非对称存储结合可以产生更好的混淆，因为它压平了层级结构并随机化了文件基名。

实现无法做到：

  • 阻止文件回滚到之前的版本
  • 阻止意外的重命名或移动
  • 阻止服务器端的删除
  • 混淆文件大小或修改时间
  • 混淆文件总数
  • 混淆远端根目录名
  • 混淆服务器键值文件元数据存储中的密钥

算法 ​

  • SHA256：从用户信息生成确定且唯一的盐，用于获得主密钥。
  • Argon2id：从盐和用户密码生成主密钥，在每次用户信息 / 密码变更时使用。
  • HKDF-SHA-256：从主密钥派生根文件密钥、名称密钥和元数据密钥，并从根文件密钥和文件盐派生文件密钥，在每次同步时使用。
  • CSPRNG：（crypto.getRandomValues()）生成随机的文件盐，在每次文件加密时使用
  • AES-GCM-256：加密文件内容和元数据值的主要算法，在每次文件加密时使用
  • AES-GCM-SIV-256：加密文件 / 文件夹名称的算法，在每次文件加密时使用
  • Base64URL：把二进制数据转换为 ASCII 以便存入文件名
  • Base64：把二进制数据转换为 ASCII 以便存入元数据值

密钥与数据结构 ​

  • 用户密码：用户密码的原始字符串
  • 认证标签（auth tag）：16B，由 AES-GCM-256 生成，用于校验数据完整性
  • 主盐（master salt）：16B，用于给用户密码加盐得到主密钥，由用户信息的 SHA256 生成
  • 主密钥（master key）：32B，由 Argon2id 从用户密码和主盐生成的确定性强密钥
  • 名称密钥（name key）：32B，从主密钥派生，用于加密文件名
  • 根文件密钥（root file key）：32B，从主密钥派生，用于为每个文件生成文件密钥
  • 元数据密钥（meta key）：32B，从主密钥派生，用于加密元数据值
  • 文件密钥（file key）：32B，从根文件密钥和随机的文件盐派生
  • 文件盐（file salt）：16B，纯随机，每次加密或解密文件时用于派生文件密钥
  • 文件密钥盐（file key salt）：32B，文件盐 || 8B 表示的加密文件大小 的 SHA256
  • 分块 nonce（chunk nonce）：12B，以 12B 表示的分块索引。
  • 加密文件 / 文件夹名：AES-GCM-SIV 加密文件名后的 Base64URL
  • 加密文件 / 文件夹路径：所有祖先层级的加密文件 / 文件夹名以 / 连接。
  • 文件分块：131,088B，文件按 128KiB 分块并经 AES-GCM-256 加密后的片段（末块可以更小）
  • 加密文件内容：文件盐 || 所有分块按顺序拼接
  • 元数据 nonce（meta nonce）：12B，纯随机，每次元数据值加密经 CSPRNG 生成
  • 加密元数据值：元数据 nonce || AES-GCM-256 密文（含 16B 认证标签）的 Base64

启用与禁用 ​

该功能通过 Encryption 设置开关。密码存储在 Obsidian 的钥匙串中。记录存储存在时，切换开关会打开确认提示，类似非对称存储；只有在你按照远程迁移指南完成远端数据迁移之后才确认。

同步流程 ​

每次同步时，生成一个 promise 来获取根文件密钥、名称密钥和元数据密钥，按需 resolve 并缓存：

  • 起始检查：发现用户密码是空字符串或 undefined 时直接抛出
  • 生成主盐：对配置的后端账户中通常可安全披露的区分数据（例如账户名 + 服务器 URL + 目录前缀）取 SHA256，截断为 16B。
  • 用 Argon2id（32MB 内存、3 次迭代、1 线程）在用户密码和主盐上生成主密钥
  • 用 HKDF-SHA-256 派生根文件密钥（info: root-file-key-v1，无盐）、名称密钥（info: name-key-v1，无盐）和元数据密钥（info: meta-key-v1，无盐）
  • 以根文件密钥、名称密钥和元数据密钥 resolve

然后进入遍历与同步逻辑：

  • 加密和解密隔离在远端文件系统包装器中。包装器透明地转换每个文件系统操作的键和内容。
  • "Encryption" 启用时假设所有文件都已加密，未启用时假设所有文件都是明文。

文件 / 文件夹路径加密 ​

  • 所有路径应以 UTF-8 表示并规范化为 Unicode NFC
  • 级联加密整条路径链，对每个文件名（应是独立名称，如 bar、foo.md）：
    • 用 AES-GCM-SIV-256 加密文件名，密钥：名称密钥，内容：文件名，nonce：固定为 file-name-v1 的 UTF-8 字节。
    • 对上述结果做 Base64URL 得到最终名称
  • 例如，加密 foo/bar/a.md 的完整路径时，先加密 foo，再加密 bar 文件夹，最后加密 a.md。
  • 用全局内存缓存加速相同路径的文件路径加密 / 解密，上限 10K 条目。
  • 不加密用户的远端根目录。

文件加密 ​

  • 输入原始文件和原始文件大小
  • 经 CSPRNG 生成随机 16B 的文件盐
  • 计算加密文件大小：原始大小 + 16B + ceil(原始大小 / 128KiB) * 16B
  • 计算文件密钥盐：文件盐 || 8B 表示的加密文件大小 的 SHA256
  • 用根文件密钥的 HKDF-SHA-256 计算文件密钥（盐：文件密钥盐，info: file-key-v1）。
  • 把文件内容切成 128KiB 的分块，末块用特殊大小，对每个分块：
    • 取从 0 开始的分块索引，以 12B 表示作为分块 nonce
    • 用文件密钥和分块 nonce 经 AES-GCM-256 加密这 128KiB
    • 每块 = 密文（128KiB = 131,072B）+ 认证标签（16B）= 131,088B
  • 把文件拼接为：文件盐 || 所有分块按顺序

元数据加密 ​

  • 用 HKDF-SHA-256 从主密钥派生元数据密钥（info: meta-key-v1，无盐）
  • 对每个非空的元数据值：
    • 经 CSPRNG 生成随机 12B 的元数据 nonce
    • 用元数据密钥和元数据 nonce 经 AES-GCM-256 加密 UTF-8 编码的值
    • 编码为元数据 nonce || 密文（含 16B 认证标签）的 Base64
  • 解密反转这个过程：Base64 解码、切分元数据 nonce（前 12B）与密文、用 AES-GCM-256 解密

一次性解密 ​

  • 输入加密文件和以字节计的加密大小
  • 切出前 16B 作为文件盐
  • 计算文件密钥盐：文件盐 || 8B 表示的加密文件大小 的 SHA256
  • 用根文件密钥的 HKDF-SHA-256 计算文件密钥（盐：文件密钥盐，info: file-key-v1）。
  • 继续切成 131,088B 的片段（末块例外），对每个片段：
    • 以分块索引作为分块 nonce
    • 用分块 nonce + 文件密钥经 AES-GCM-256 解密该块，认证标签不匹配时抛出 Decryption error: incorrect encryption password or the data is corrupted 并跳过该文件
  • 拼接解密后的内容

流式解密 ​

流式解密接收一个 ReadableStream，生成另一个 ReadableStream，在流之间管道式解密。

  • 输入以字节计的加密大小，并接受文件内容的顺序二进制流
  • 内部拆分并拼接分块
  • 例如，收到的第一个二进制大小为 2,000,000B 时，range 解密器：
    • 剥离前 16B 作为文件盐
    • 为每个分块累加计数器，剥下接下来的 1966380B 作为 15 个已完成分块
    • 把最后 33604B 保存为一个未完成分块，存入缓冲区
    • 像一次性解密那样解密这 15 个已完成分块
    • 拼接内容，并管道输出到新流。
    • 下一个二进制流分块到达时，它把缓冲区中的内容与新二进制的开头一定数量的字节拼接，作为第一个已完成分块。
    • 重复直到原始流结束，此时类把缓冲区中剩余内容视为一个已完成分块，直接解密，管道输出到新流，然后结束它。

流式加密 ​

流式加密与流式解密走对称的路径。

  • 输入以字节计的未加密大小和文件内容的 ReadableStream。
  • 计算加密大小：原始大小 + 16B + ceil(原始大小 / 128KiB) * 16B
  • 计算文件密钥盐：文件盐 || 8B 表示的加密文件大小 的 SHA256
  • 用根文件密钥的 HKDF-SHA-256 计算文件密钥（盐：文件密钥盐，info: file-key-v1 常量字符串）。
  • 在原始流之上创建一个 TransformStream。
  • 持续读取流，加密并维护一个原始字节缓冲区：预留一个流分块后缓冲区不足 128KiB 时继续读取；大于 128KiB 时，加密缓冲区中最多数量的 128KiB 分块并发出。流结束时，加密并发出缓冲区中的剩余内容。
  • 第一个发出的内容前面应带文件盐。

文件 / 文件夹名解密 ​

  • 输入文件名并做 Base64URL 解码得到原始字节
  • 用 AES-GCM-SIV-256 配合名称密钥和 nonce 解密文件名的其余部分（尽量使用缓存）

实现 ​

实现只应使用：

  • Web Crypto
  • hash-wasm 的 argon2id 导出
  • @noble/ciphers/aes.js 的 gcmsiv 导出

加密功能会作为一个 Sync Engine 可选模块干净地集成在 encryption 包内，它提供一个 RemoteFsWrapper：

第二个参数接收内存数据库实例和用户密码。

getUid()、checkConnection()、options：保持原样。

read()：转发给原始 FS 之前加密键，原始 FS 返回后解密。

readStream()：转发给原始 FS 之前加密键，创建一个新的 transformStream 中继原始流。

write()：转发给原始 FS 之前加密键、内容和元数据值。

writeStream()：转发给原始 FS 之前加密键、元数据值和流内容。

delete()、mkdir()：转发给原始 FS 之前加密键。

stat()：转发前加密键，原始 FS 返回后解密 Stat 中的 key 和元数据值。

list()：转发前加密键，原始 FS 返回后解密 Array<Stat> 中的 key 和元数据值。

路径段和派生密钥会被缓存，跨同步运行持久化。缓存基于从 context 获取的 Uni-KV memoryDB，类似 Context 包装器，只在信号变化时重置：

  • 存储元数据：EncryptionDBMeta
  • 存储模式：EncryptionDBSchema
  • 作用域：decryptedToEncrypted 和 encryptedToDecrypted 存储

行为：

  • context 的 memoryDB 类型不同，把它转型为 MemoryDatabase<EncryptionDBSchema, EncryptionDBMeta>。
  • encryptionMarker = RemoteFs.getUid() || ~ || 用户密码
  • 缓存的派生密钥保存在 store meta 的 encryptionKeys 字段中
  • 仅在包装器激活时执行一次：检查 store meta 的 encryptionMarker 是否与当前一致。不一致时清空存储和 encryptionKeys，并把元数据更新为当前 uid。
