项目纪律 ​

数据规范化 ​

数据规范化指把来自外部源的数据转换成 Sync Engine 内部使用的规范形式。

  • 对"不可靠"的条目（用户输入，或由众多服务器实现的标准），所有需要规范化的数据必须在入口点精确地、且仅一次地完成规范化。Sync Engine 内部不应再做任何规范化。
  • 对"可靠"的条目（由单一供应商实现的专有 API），完全不应做规范化。

特殊数据分为以下几类，无论来源可靠性如何都必须规范化：

  • 文件大小：转换为字节数的单一数字。面向用户的展示转换为数字 + 空格 + 大写单位，例如 1 GB、537 MB、29.9 KB，以 1024 为基数（严格来说单位是 KiB/MiB/...，但为便于理解使用不带 i 的单位），最多 2 位小数。
  • 时间长度：毫秒精度的整数 Unix 时间戳。面向用户的展示使用数字 + 空格 + 小写单位，例如 1 s、24 h、2.3 d，最多 2 位小数。
  • 文件路径（键）：遵循统一键——folder/file.ext，文件夹 - folder/nested/，根：/。规范化为 Unicode NFC。
  • URL：所有 URL 的路径名、查询参数和片段按 RFC 3986 百分号编码；协议和主机名中的 ASCII 拉丁字母转为小写。面向用户的展示对路径名、查询参数和片段做解码。
  • 请求 / 响应头键：尽可能使用 kebab-case。用户自定义的键保留原大小写。
  • ETag：剥离 W/ 弱 ETag 标记和两侧引号。

文档 ​

  • 主文档位于 docs/src/pages/en/，分三个文件夹对应三个部分：usage/、development/ 和 deep-dive/：
    • usage/：面向非技术用户，避免行话
    • development/：只放 SDK API 参考和实用的模块开发设置
    • deep-dive/：Sync Engine 内部机制
  • 其他页面有相关内容时优先使用页面间链接，禁止跨页重复内容。
  • 链接格式：尽可能链接标题锚点，严格的相对链接，不带 .md 扩展名。
  • 只在内容真正相关时添加页间链接，不得为了链接数量而链接远处的页面。
  • 链接拓扑：
    • usage/ 和 deep-dive/ 可以互链
    • development/ 可以链接到 usage/ 和 deep-dive/，但 usage/ 和 deep-dive/ 应避免链接进 development/。
    • 模块规范（deep-dive/modules/*）应在各自页面内自包含。它们可以链接外部页面，但外部页面不应链接官方模块，usage/ 中的专门页面除外。
  • 不要过度冗长。
  • usage/ 和 deep-dive/ 避免大段代码，代码应作为 development/ 的主体内容。
  • 文档标题使用 title case。

代码风格 ​

  • 只允许 JSDoc 注释硬换行（在句子中间断行）。
  • 其他注释首选单行。需要多行时，每行必须是完整的句子。
  • 注释行可以超出打印宽度限制。
  • 能提升简洁性时优先使用解构。
